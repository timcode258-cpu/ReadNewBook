## 一、课前补一条：事件状态不累计通知次数

自动重置事件暂时无人等待时，第一次SetEvent把它设为有信号，第二次SetEvent只是再次设置同一个已经有信号的对象。事件没有一个“已通知两次”的计数器。

可以把它暂时想成一盏指示灯：已经亮着时再按“点亮”，不会留下第二盏灯。之后一个等待成功消耗信号，就变回无信号；其他等待者仍需后续通知。这个比喻只解释两种状态，不表示所有通知工具都像灯。

对自动事件而言，若前一个信号已被某个等待成功消耗，之后再SetEvent，才会产生新的放行机会。不要仅数调用次数，要同时看中间有没有等待消费了信号。多个等待者谁先通过也没有固定顺序，不应理解成保证均匀随机。

## 三、把“加一次”拆开，谁覆盖了谁？

下面是助手定义的抽象调度模型，用来推演覆盖写回：

- 共享数字n初始为0。
- A和B各做一次：读n到自己的临时变量 → 临时值加1 → 写回n。
- 每个小步骤不可分割，整个三步可以与另一线程交错。
- 最后等A/B都结束，再看n。除题目给出的步骤外没有其他读写。

这不是承诺真实C++的n++一定编译成三条指令，或有数据竞争时仅会得到这些结果；先在这个明确的小模型里理解覆盖。

看一种具体交错：

| 步骤 | 谁执行什么 | A私有临时值 | B私有临时值 | 共享n |
|---:|---|---:|---:|---:|
| 1 | A读n | 0 | — | 0 |
| 2 | B读n | 0 | 0 | 0 |
| 3 | A把自己的临时值加1 | 1 | 0 | 0 |
| 4 | B把自己的临时值加1 | 1 | 1 | 0 |
| 5 | A写回n | 1 | 1 | 1 |
| 6 | B写回n | 1 | 1 | 1 |

两条线程都加了1，但它们各自拿到同一个旧值0，最后两次写回的是同一个1；其中一次更新被覆盖。这叫丢失更新。

如果A先完整做完三步，B再读到1并加1，最终就是2。因此在这个模型中，最终可能为1或2；各只加一次就足够产生问题。大量循环只会增加遇到问题的机会，不是错误发生的必要条件。

单核上的步骤交错就能演示这个问题，多核上还可能真正同时执行。不能用“看起来只是一行代码”推断整个读改写已经受到保护。

## 四、等线程都结束，为什么救不回这次更新？

等待线程结束解决的是“它是否还在执行”，不会重做它们之前已经互相覆盖的写入。主线程可以可靠地等到A/B都结束，然后读到错误的最终值。

同样，Sleep、PostMessage报告进度、共享变量声明为全局，都不能自动把这三个步骤合成一个受保护的整体。

现实C++里，多个线程无相应同步地读写同一普通变量、至少一方在写，可能构成数据竞争并导致未定义行为，不能把上面的1/2结果表当成真实无同步C++程序的完整保证。原书使用调试/优化版本观察现象，某次结果正常也不证明程序线程安全。

## 五、原书的第一种修复：Interlocked

同一节Interlocked小标题下的原文：

> 就上面的ThreadSync示例而言，最简单的线程同步方式是使用Interlocked原子访问系列函数。InterlockedIncrement、InterlockedDecrement这两个函数可以保证以原子方式对多个线程的共享变量进行递增、递减操作：

原型仅统一空白：

```cpp
LONG InterlockedIncrement(_Inout_ LONG volatile* Addend);
LONG InterlockedDecrement(_Inout_ LONG volatile* Addend);
```

“原子递增”表示从其他相关并发操作观察，读取、加1、写回这一整次更新不可被拆开交错，避免两次递增共同覆盖旧值。它不表示整条线程从此不能被调度走，也不保护其他未纳入的变量或代码。

助手的Windows用法片段：

```cpp
LONG n = 0;  // 共享对象，按要求对齐，寿命覆盖两个线程的使用

// 线程A执行一次：
LONG resultA = InterlockedIncrement(&n);

// 线程B执行一次：
LONG resultB = InterlockedIncrement(&n);

// 主线程成功等待A/B都结束后，再读取最终n
```

这些是各线程对应的片段，不是让同一线程按此顺序执行，也不是完整工程。假定没有其他修改、各并发修改均使用此原子机制，最终n为2。先发生的那次递增得到1，后发生的得到2，A/B谁先不作保证。

接口接收变量地址&n，返回本次递增后的值，不是BOOL成功标志。要使用接口要求的、正确对齐的LONG对象；本接口处理32位值，不要把任意地址强行转成LONG指针使用，64位值有对应的64位接口。

原型中的volatile不等于“加上它就保证原子”。只给普通变量加volatile，不能把n++变成原子递增；应使用相应同步/原子机制。原书这部分关于volatile的简化解释，不能替代这个保证。MSVC的volatile扩展与标准C++还有差别，本课先不依赖这些扩展来实现共享递增。

InterlockedIncrement和InterlockedDecrement分别原子，也不等于两句合起来作为一个整体受到保护；需要保护连续多步或多个相关数据时，下一步学习关键段等机制。

## 六、用对工具，分别解决不同问题

| 需要保证的事 | 本课对应工具/方法 |
|---|---|
| 允许工作开始 | 事件等通知机制，业务条件由程序约定 |
| 知道线程已结束 | 等待线程对象并检查结果 |
| 共享数字加1不丢更新 | 对所有相关访问采用正确的原子/同步方案，本课例子用InterlockedIncrement |
| 多步操作共享数据期间不被其他参与者插入 | 需要保护整个操作区间，下一步讲关键段 |
