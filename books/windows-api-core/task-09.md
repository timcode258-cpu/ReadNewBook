# 任务09：线程的挂起与恢复

日期：2026-11-04。对应本书1.3后半部分，建议阅读12分钟、两问3分钟；继续静态学习，不要求运行。本课目标：能算清挂起计数，并区分暂停、结束和等待。

## 一、先有一个具体场景

主线程想先创建工作线程，准备好数据后，再允许它开始执行线程函数。可以在CreateThread的第5个参数指定CREATE_SUSPENDED，让新线程先处于挂起状态。

“挂起”表示暂时不让线程执行应用代码；线程并没有因此正常返回或完成工作。“可调度”表示具备获得CPU执行的资格，具体什么时候轮到它，由系统安排。

下面是助手提供的调用顺序，假设数据始终有效、所有调用成功、没有其他线程修改挂起计数：

```text
主线程：CreateThread(..., CREATE_SUSPENDED, ...)
        得到线程句柄h；工作线程尚未进入Worker
主线程：完成Worker所需数据的准备
主线程：ResumeThread(h)
        挂起计数从1减到0，工作线程可以被调度
工作线程：获得执行机会后进入Worker，执行工作，最后return
主线程：等待并检查结果，确认工作线程结束
主线程：如有需要，查询退出码并检查查询是否成功
主线程：不再需要h时关闭句柄，最后退出
```

这里由主线程恢复工作线程；工作线程不需要先跑起来才能接受这次恢复。主线程中的“恢复”调用也不承诺Worker已经执行完任何一行代码。

## 二、对应原文

来源：王端明《深入浅出Windows API程序设计：核心编程篇》1.3，EPUB/xhtml/Chapter01_0004.xhtml，以以下段落开头定位。三段原文保留措辞，函数原型只统一空白与缩进。

> 当调用CreateThread函数创建线程时，如果dwCreationFlags参数指定了CREATE_SUSPENDED标志，那么线程创建后并不马上开始执行，而是处于被挂起状态，直到调用ResumeThread函数启动它为止。调用ResumeThread函数可以减少线程的挂起计数，当线程的挂起计数为0时，线程成为可调度状态：

```cpp
DWORD WINAPI ResumeThread(_In_ HANDLE hThread);
```

> 如果函数执行成功，则返回值是线程的先前挂起计数；如果函数执行失败，则返回值为−1。

> 一个线程可以被挂起（暂停），也可以在挂起后恢复执行。除在创建线程时使线程处于挂起状态外，也可以调用SuspendThread函数将正在运行中的线程挂起。SuspendThread函数用于挂起指定的线程，并增加线程的挂起计数：

```cpp
DWORD WINAPI SuspendThread(_In_ HANDLE hThread);
```

SuspendThread同样在成功时返回先前的挂起计数。以下是助手解释和当前官方接口核对。

## 三、为什么恢复一次，有时还没恢复执行？

线程有一个“挂起计数”，本课把它看成记录暂停层数的数字：

- SuspendThread成功：计数加1。
- ResumeThread成功：若计数大于0，就减1；本来为0时仍为0。
- 计数大于0：仍然挂起。减到0：解除这项暂停限制，可以被调度。

例子：刚用CREATE_SUSPENDED创建成功时，挂起计数为1。主线程又成功调用两次SuspendThread，再逐次恢复：

| 操作 | 调用前计数 | API返回值 | 调用后计数 | 对工作线程的含义 |
|---|---:|---:|---:|---|
| 第一次SuspendThread | 1 | 1 | 2 | 仍然挂起 |
| 第二次SuspendThread | 2 | 2 | 3 | 仍然挂起 |
| 第一次ResumeThread | 3 | 3 | 2 | 仍然挂起 |
| 第二次ResumeThread | 2 | 2 | 1 | 仍然挂起 |
| 第三次ResumeThread | 1 | 1 | 0 | 可以被调度 |

**返回的是调用前的计数，不是调用后的计数。** 这里返回3、2、1都表示调用成功；返回1的那次，才把计数减到0。

助手绘制的计数变化图：

```mermaid
flowchart LR
    A[挂起计数3] -->|Resume 返回3| B[挂起计数2]
    B -->|Resume 返回2| C[挂起计数1]
    C -->|Resume 返回1| D[挂起计数0<br/>可以被调度]
```

对于仍存活、未挂起的线程，ResumeThread成功返回0，表示调用前计数已经是0；这不是查询退出码的BOOL约定。两种挂起/恢复API失败时返回(DWORD)-1，此时应立即取得错误信息。不要用if(result)统一判断它们是否成功。

```cpp
DWORD previous = ResumeThread(h);
if (previous == (DWORD)-1)
{
    DWORD error = GetLastError();
    // 保存或报告错误，不能据此认为恢复成功
}
else
{
    // previous是调用前的挂起计数
}
```

这是控制流片段，不是完整可运行工程。成功恢复也不证明工作线程已经结束；要确认结束，仍使用之前学过的等待结果。

## 四、暂停、等待、结束：谁在停下来？

| 操作或状态 | 影响谁 | 会让工作线程执行收尾并正常return吗？ |
|---|---|---|
| 主线程等待工作线程结束 | 等待中的主线程暂时不能越过等待点 | 工作线程照常执行，是否正常收尾取决于它的代码 |
| 主线程挂起工作线程 | 工作线程被暂停 | 不会替它执行清理或return |
| 请求工作线程自行结束 | 工作线程观察请求后按程序逻辑行动 | 可以让它在合适位置收尾并return，最后仍需确认完成 |

如果工作线程一直挂起，没有任何线程恢复它，也没有其他终止事件，主线程无限等待它结束，就会一直等着。等待函数不会帮忙恢复工作线程。

## 五、为什么不把SuspendThread当普通业务的暂停按钮？

工作线程可能正拿着其他线程需要的资源。例如“锁”是一种控制共享资源访问的机制：线程A占用期间，线程B可能必须等A释放它，才能继续使用。

如果主线程把拿着锁的工作线程挂起，又自己等这把锁；而负责恢复工作线程的后续代码也在主线程中，那么主线程等锁、工作线程等恢复，双方都无法继续。这叫死锁。

因此微软将SuspendThread主要用于调试器，不建议把它作为普通线程同步手段。业务中的暂停/结束通常让工作线程接收请求，在自己确认合适的位置响应；具体通知机制在后续同步内容里学习。本节先掌握接口含义和边界。

调用挂起/恢复还要求句柄具有THREAD_SUSPEND_RESUME权限，不是拿到任何线程句柄都能操作。
